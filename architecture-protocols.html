1Chosen pattern: MVVM with a Repository layer

We will build Ortak Hesap in Flutter and organise the code with MVVM (Model–View–ViewModel) plus a Repository layer between the ViewModels and the data sources. Flutter UIs are declarative: a widget is a function of state. MVVM fits this naturally, because the View only renders state exposed by a ViewModel and forwards user events back to it. In classic MVC the controller would have to push updates into the view, which is awkward in Flutter and tends to mix widget code with business logic. Keeping the logic in ViewModels makes it testable without a device. Alternatives such as BLoC or Redux would also work, but they add more boilerplate than a two-person project needs; we use provider with ChangeNotifier, which is simple and taught in the course.

5Algorithms in the Model layer

Money and equal split. Amounts are integers in kuruş (₺86,90 = 8690). For n people, each share is floor(total / n) and the total mod n remaining kuruş go one by one to the first members. Example: 8690 / 4 → 2173, 2173, 2172, 2172, which always sums to the total (this matches the numbers in the mockups).

Balance of a member = what they paid − their shares + settlements received − settlements paid. Balances sum to zero within a group.

Simplifying debts (greedy, at most n−1 payments):

creditors = members with balance > 0
debtors   = members with balance < 0
while both lists are not empty:
    c = creditor with the largest balance
    d = debtor with the largest |balance|
    pay = min(c.balance, |d.balance|)
    emit "d pays c: pay"
    c.balance -= pay;  d.balance += pay

Flat 4B: You +120, Ayşe −80, Mert −40, Can 0 gives two payments (Ayşe→You 80, Mert→You 40), as shown on screen S7.

7Security, offline behaviour and testing

  • Authorisation: Firestore Security Rules allow a user to read or write groups/{gid} and its sub-collections only if their uid is in memberIds; expenses must pass a server-side check that shares sum to the amount.
  • Privacy: only the minimum personal data is stored (name, e-mail); receipt images are private; sign-out removes the local cache and the FCM token.
  • Offline-first: writes go to the local Firestore cache first and sync later; the UI shows a “Waiting to sync” chip (see the user flow edge cases).
  • Testing: unit tests for money rounding and the debt solver (with property tests: balances sum to zero, at most n−1 payments), ViewModel tests with fake repositories, and widget tests for S5, S6 and S7.
Known limitation. Server-side push needs a Cloud Function, which requires Firebase’s pay-as-you-go plan. If we stay on the free plan for the course, the app will fall back to Firestore listeners and local notifications while it is open, and push will be demonstrated with a test message from the Firebase console.
